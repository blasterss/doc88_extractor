# История исследования формата DOC88

Этот документ описывает, как исследовались данные предпросмотра DOC88 и как
появился конвейер EBT → SWF → PDF. Текст переведён и отредактирован по исходной
китайской заметке автора проекта.

## С чего всё началось

Автор хотел сохранить экзаменационные материалы, которых на DOC88 было много и
которые можно было просматривать в браузере. Обычные найденные инструменты
сохраняли лишь изображения страниц или печатали их через сторонние программы.
Поэтому формат предпросмотра пришлось исследовать самостоятельно.

## Поиск файлов документа

Во время прокрутки страницы браузер постоянно загружал файлы с именами, похожими
на Base64. Обычный Base64 их не декодировал. Анализ JavaScript показал две
нестандартные таблицы символов: одну для данных конфигурации, вторую для имён
файлов.

После декодирования имена выглядели примерно так:

```text
1-0-455235-63-20110912-20110912175543_7SOoC87j
1-455235-3936-63-20110912-20110912175543_7SOoC87j-1-69091550288
1-455235-3936-63-20110912-20110912175543_7SOoC87j-2-69091550288
1-455235-3936-63-20110912-20110912175543_7SOoC87j-3-69091550288
```

Предпоследнее поле росло как номер страницы, последнее совпадало с ID документа,
а часть полей относилась к дате и идентификатору SWF.

В HTML страницы обнаружился вызов `m_main.init(...)`. Его аргумент был
закодированной конфигурацией `Config`. После декодирования стали доступны
`pageInfo`, метаданные документа, адрес CDN и сведения о заголовках. Первоначальный
конвейер загрузки получился таким:

```text
URL → конфигурация страницы → список страниц → заголовки PH → страницы PK
```

## Что находится в EBT

Первый файл имел сигнатуру `YBD`, остальные не имели очевидного заголовка.
Разобраться помогли материалы:

- [EBT: введение](https://blog.csdn.net/WinsenJiansbomber/article/details/47051233);
- [основа загрузчика EBT](https://blog.csdn.net/winsenjiansbomber/article/details/47065697);
- [набор инструментов EBT](https://blog.csdn.net/WinsenJiansbomber/article/details/47284463).

Просмотр DOC88 тогда был реализован на Flash. Заголовок PH и данные страницы PK
можно объединить в SWF. Сохранившийся инструмент DDA также подтвердил порядок
обработки:

- [DDA — Doc88 Downloader AIR](https://archive.org/details/dda_doc88_cracker);
- [архив программы](https://edge.piglin.eu.org/dda_doc88_cracker.zip).

В старой программе обнаружилась особенность интерфейса: корректный результат
получался только при выборе PH и PK в нужном порядке. После переноса алгоритма
из ActionScript в JavaScript, а затем в Python выяснилось, что одна из ранних
версий конвертера ошибочно добавляла заголовок `FWS` дважды.

Фактическая обработка оказалась простой:

1. из PH пропускаются первые 40 байт, остаток распаковывается через zlib;
2. из PK пропускаются первые 32 байта, остаток также распаковывается;
3. обе распакованные части объединяются в SWF.

То есть содержимое не зашифровано в криптографическом смысле: SWF разделён на
две части, а части отдельно сжаты и снабжены служебными заголовками.

## Преобразование SWF

SWF можно открыть Flash-проигрывателем и напечатать в PDF, но ручная обработка
каждой страницы неудобна. Первые попытки прямого экспорта через ffdec сохраняли
картинки и часть фигур, но теряли текст. Экспорт в SVG выглядел точнее, поэтому
ранняя версия использовала следующий маршрут:

```text
SWF → SVG через ffdec → PDF через CairoSVG → объединение страниц
```

Некоторые SWF имели нулевое число кадров в заголовке, из-за чего ffdec ничего не
экспортировал. После исправления заголовка такие страницы обрабатывались
нормально. Другой класс проблем был связан с фигурами, которые ffdec неверно
разбирал и отображал как большие белые области.

Позже в ffdec улучшили обработку предоставленных примеров. Прямой экспорт в PDF
стал сохранять текст, изображения и фигуры заметно лучше. Возможность SVG
осталась запасным маршрутом, а преобразование SVG → PDF теперь выполняет
написанная на Rust утилита `svg2pdf`.

Опция `font-face` позволяет получить выделяемый текст в SVG, но у неё есть
компромиссы: возможны смещения, замена шрифтов, нечитаемые символы и ошибки
отдельных фигур.

## Документы длиннее 50 страниц

В ранней версии страницы после 50-й не распаковывались. Сначала возникло
предположение, что каждые 50 страниц образуют новый уровень. Например:

```text
2-0-453032-63-20110912-20110912175543_7SOoC87j
2-453032-3261-63-20110912-20110912175543_7SOoC87j-51-69091550288
```

Но разные документы делились на уровни по-разному. Ответ уже находился в
`pageInfo`:

```text
1-595-841-455235-3936
1-595-841-459171-2914
1-595-841-462085-2840
2-595-841-453032-3261
2-595-841-456293-3496
```

Первое число задаёт уровень PH. `595-841` — ширина и высота документа. Следующее
число является смещением страницы, последнее — размером её блока. В пределах
уровня смещение следующей страницы равно смещению текущей плюс размер текущего
блока. При переходе к новому PH отсчёт начинается заново.

Так загрузчик перестал вычислять уровни эвристически и начал брать их напрямую
из `pageInfo`.

## Поиск дополнительных страниц

Иногда `pageCount` не совпадал с количеством элементов `pageInfo`: сайт
показывал лишь часть документа или первую страницу каждого уровня. Выяснилось,
что CDN может отдать больший непрерывный диапазон, содержащий PH и несколько PK.

Границы сжатых блоков ищутся по заголовку zlib. Двух байт заголовка недостаточно
для надёжного совпадения, поэтому каждый кандидат дополнительно проверяется
распаковкой и контрольной суммой zlib. Если распаковка успешна, найденный блок
можно объединить с PH и восстановить ещё одну страницу SWF.

Благодаря этому документ иногда удаётся обработать целиком, даже если в
стандартном предпросмотре перечислена только часть страниц. Возможность зависит
от того, какие данные фактически доступны на сервере.

## Текущее состояние

Поиск дополнительных страниц реализован. Основные дальнейшие задачи:

1. сделать кеш и возобновление операций устойчивее;
2. отделить сетевую загрузку от преобразования и интерактивного интерфейса;
3. добавить автоматические тесты для кодека, разбора конфигурации и сборки SWF;
4. улучшить диагностику ошибок внешних инструментов.
